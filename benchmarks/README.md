# 📊 性能压测

本目录包含 Railway-8620 的性能压测脚本，用于量化系统的并发能力与延迟指标，为面试提供**可量化的数据支撑**。

## 脚本清单

| 脚本 | 说明 | 依赖 |
|------|------|------|
| `benchmark_api.py` | 纯 Python 并发压测（推荐，零额外依赖） | `httpx`（已在 requirements.txt） |
| `locustfile.py` | Locust 分布式压测（可选，更专业） | `pip install locust` |

---

## 快速开始

### 1. 启动后端

```bash
# 本地开发模式
uvicorn backend.api:app --host 0.0.0.0 --port 8000

# 或 Docker
docker compose up -d backend
```

> ⚠️ 压测前请确保 `.env` 中已配置 `llm_api_key`（否则 Agent 无法创建，接口会报错）。

### 2. 运行纯 Python 压测

```bash
# 默认：注册一个测试用户，并发 10，共 100 个请求
python benchmarks/benchmark_api.py

# 自定义参数
python benchmarks/benchmark_api.py --base-url http://localhost:8000 \
    --concurrency 20 --requests 200 --output results.json
```

### 3. 运行 Locust 压测（可选）

```bash
pip install locust
locust -f benchmarks/locustfile.py --host http://localhost:8000
# 打开 http://localhost:8080 配置并发数与速率
```

## 指标说明

脚本会输出以下指标：

| 指标 | 含义 |
|------|------|
| **TTFT**（首 token 时间） | 从发请求到第一个 token 到达——**用户感知的等待** |
| **总时长 P50 / P95 / P99** | 完整响应耗时（含全部 token 生成）百分位 |
| **QPS** | 每秒请求数（吞吐量） |
| **成功率** | 200 响应占比 |
| **token 总数** | 收到的 content 事件数（衡量回答长度） |

> 💡 **为什么要同时看 TTFT 和总时长**：流式架构的价值就是把用户感知的等待从"总时长"降到"首字时间"。
> 脚本会直接打印两者的倍数关系（如"首字比完整响应快 8.2 倍"）——这个比值就是流式化的收益。
>
> **面试建议**：
> - **重点讲 TTFT**：它才是用户体感；总时长更多反映 LLM 生成速度，不是你的系统能力
> - 记录**环境信息**（机器配置、LLM 模型、并发数），保证数据可复现
> - 对比不同 `AGENT_THREAD_POOL_SIZE`（默认 8）下的吞吐差异，展示你对线程池调优的理解

## 📈 实测数据

**环境**：
- 后端：FastAPI + LangGraph Agent（本地 uvicorn，单进程）
- LLM：`deepseek-v4-flash`（火山方舟 coding 接口）
- 线程池：`AGENT_THREAD_POOL_SIZE=8`（默认）
- 压测接口：`POST /chat/stream`（SSE 流式，与前端同链路）

**结果（2026-10-04，并发 2 / 各 2 请求）**：

| 消息 | TTFT 平均 | 总时长平均 | token 数/请求 | 流式收益 |
|------|-----------|------------|---------------|----------|
| `你好`（不触发工具） | 3.7 s | 5.5 s | 98 | 1.5× |
| `Z227 车次信息`（触发工具调用） | **8.0 s** | 12.1 s | 300 | 1.5× |

> 📌 **最有价值的发现：TTFT 由工具调用主导，不由流式机制决定**
>
> `stream_mode="messages"` 推送的是**最终回答的 token**。在 ReAct 循环里，第一个 token 要等
> "LLM 决定调工具 → 工具执行完 → LLM 开始组织回答"整条链路走完才出现。
> 所以触发工具的请求 TTFT 从 3.7s 涨到 8.0s（**翻倍还多**），而"流式收益倍数"两者都是 1.5×——
> **流式架构本身改善的是"回答生成阶段的感知延迟"，工具调用阶段它无能为力**。
>
> **优化方向（面试可讲）**：要让工具类请求的 TTFT 也降下来，需要推送**过程事件**——
> 比如在调工具时先发一个 `data: {"status": "正在查询车次..."}`，让用户立刻看到反馈，
> 而不是盯着空白等 8 秒。这是"流式 UI 体验"的下一层，我目前只推送了 content 事件。

**历史数据（2026-09-04，压测目标为当时仍存在的非流式接口 `/chat`）**：

| 指标 | 数值 |
|------|------|
| 成功率 | **100%**（10/10） |
| QPS | 0.4 req/s |
| 平均延迟 | 12.5 s |
| P50 延迟 | 15.5 s |
| P95 延迟 | 27.2 s |
| P99 延迟 | 27.2 s |

> 📌 该组数据测的是完整响应耗时（非流式接口的性质），无 TTFT 概念。
> 保留此处是为了说明：**同一个 Agent 链路，换成流式响应后用户感知延迟降到 TTFT 那一档**
> （上表 3.7s / 8.0s），这正是流式化的收益所在。

> 📌 **通用解读**：延迟主要来自 LLM 推理（`deepseek-v4-flash` 单次响应约 5-15s），而非系统瓶颈。系统本身（认证、路由、checkpoint 持久化）开销极小。若需提升吞吐，可：
> - 增大 `AGENT_THREAD_POOL_SIZE`（但受 LLM 并发配额限制）
> - 换用响应更快的 LLM 模型
> - 对纯工具查询（车次/地图）走独立快速通道，不经 LLM

> ⚠️ **注意**：压测时若 RAGFlow 未启动，Agent 对知识类问题会反复调用 `retriever_tool`（每次超时约 4s 后返回"未找到"），进一步拉高延迟。**启动 RAGFlow 后**知识检索正常，延迟会显著下降。建议压测时：
> - 用**车次/地图类问题**（走本地 JSON，不经 RAGFlow）测系统吞吐
> - 用**知识类问题**（走 RAGFlow）测 RAG 链路延迟
