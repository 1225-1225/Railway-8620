# 第一部分：项目整体类提问

## Q1.1 介绍一下这个项目（⭐ 必考，开场题）

**参考回答（60-90 秒版）**：

> 这是我独立开发的一个铁路领域智能问答系统，解决的问题是：铁路知识分散在 200 多篇文档里、车次时刻数据量大且每天变化，传统搜索无法直接回答"Z227 几点到北京"这类问题。
>
> 架构上分四层：**Agent 层**用 LangGraph 构建 ReAct 循环，接了知识检索、车次查询、路线推荐、地图生成四个工具；**API 层**用 FastAPI 提供 SSE 流式接口，重点解决了同步 Agent 代码和异步 Web 框架配合时的阻塞问题；**数据层**用 SQLite 保存多轮对话记录，开了 WAL 模式让多线程读写不互相阻塞；**前端**用 Vue 3 做流式渲染和会话管理。
>
> 工程化方面，我建了 90 个自动化测试的四层测试体系、跑了压测定位性能瓶颈、修了三个自己代码审查发现的线上隐患，还做了一个 GPL 许可隔离的数据同步子项目实现车次数据每日自动更新。

**要点**：问题 → 架构 → 工程化，三段式。不要一上来就讲细节。

## Q1.2 为什么做这个项目？解决什么痛点？

> 三个痛点：① 铁路知识（机车型号、历史）散落在大量文档中，关键词搜索给不出直接答案；② 车次时刻数据每天变，静态数据会过期；③ 纯 LLM 回答会幻觉——Z227 的时刻它不知道，必须接真实数据源。所以架构上必然是"LLM 推理 + 工具查真实数据"的 Agent 形态，而不是纯 RAG 或纯对话。

## Q1.3 为什么选 LangGraph 而不是 LangChain / 自己写循环？

> 三个理由：
> 1. **对话状态的保存和恢复是框架自带的**——SqliteSaver 拿来就能用，每一步自动保存对话快照，多轮记忆不用自己写；
> 2. **图结构天然表达 ReAct 循环**——LLM 节点 ⇄ 工具节点的循环、终止条件（无 tool_calls）都是框架内建的；
> 3. **状态可检查**——`get_state()` 能读任意 thread 的当前状态，这是我实现"中断修复"机制的基础，自己写循环很难做到。
>
> LangChain 裸用的话循环逻辑、记忆、状态恢复都要手写；自己写循环则失去了生态（工具绑定、消息协议）。

## Q1.4 为什么用 SQLite 而不是 MySQL/PostgreSQL？

> 三个考量：
> 1. **部署零运维**——单文件数据库，Docker 里不用多起一个数据库容器，演示和迁移都是复制文件；
> 2. **规模匹配**——用户库几千行、checkpoint 按会话存，SQLite 的量级绰绰有余；
> 3. **并发够用**——开了 WAL 模式后读写不互斥，20 线程并发测试无锁错误（这是测过的）。
>
> 架构上用户库走 SQLAlchemy，换 PostgreSQL 只改连接串；checkpointer 是 LangGraph 的抽象，也有 PostgresSaver 实现。**瓶颈真到了再换，不为演示项目过度设计。**

## Q1.5 这个项目最难的点是什么？（⭐ 高频）

> 按难度排序：
> 1. **同步 Agent 代码与异步 Web 框架的配合**——LangGraph 的 stream 是同步阻塞的，直接放进 FastAPI 的 async 端点会冻结整个事件循环。解法是固定大小的线程池 + 结束标记对象 + 两层超时控制，这套方案前后调整了好几轮；
> 2. **损坏会话的自动修复**——流式超时中断会在 checkpoint 里留下"未闭合的 tool_calls"，下次请求 LLM 直接拒绝，会话永久损坏。解法是请求前检测 + invoke(None) 从中断处补完工具执行；
> 3. **开源许可合规**——想复用一个 GPL-3.0 爬虫项目的能力，最终用"独立子项目 + 原创实现 + 数据文件交互"做隔离。
>
> 共同点是：**都不是"不会写"，而是"写了之后在并发/异常/合规场景下会坏"**——这类问题只有压测和代码审查能暴露。

## Q1.6 如果重做一遍，你会改什么？

> 三点：
> 1. **一开始就写压测脚本**——session_id 那个全接口 500 的 bug 是压测才发现的，如果 TDD 从第一天写，能省一轮排查；
> 2. **RAGFlow 检索失败时快速放弃**——现在 RAGFlow 挂掉时 Agent 会反复重试检索（每次 4 秒超时），拉高整体延迟。应该在工具层加失败计数：连续失败 N 次后直接返回"知识库暂不可用"；
> 3. **前端 SSE 解析的跨包缓冲**——这个是后来代码审查发现的，如果一开始就按 SSE 规范写缓冲区，就不用补修。

# 第二部分：Agent 架构类提问（职责 1）

## Q2.1 ReAct 循环是怎么工作的？（⭐ 必考）

> LangGraph 的 create_agent 内部是一张两节点图：**LLM 节点 ⇄ 工具节点**。
>
> 流程：用户消息进来 → LLM 节点判断"要不要调工具"→ 需要就输出带 tool_calls 的 AIMessage → 工具节点执行 → 结果包装成 ToolMessage 写回消息列表 → 回到 LLM 节点 → LLM 看着真实数据继续推理 → 直到输出**不带 tool_calls** 的回答 → 循环终止。
>
> 实测例子：问"Z227 的信息"，第一轮 LLM 调 query_train_info 拿到时刻表，第二轮 LLM 拿着真实数据组织回答。组合意图如"查信息并画地图"会跑三轮：查信息 → 画地图 → 总结。

**追问：LLM 怎么知道该调哪个工具？**
> 两个信息源：① 每个工具的 `@tool(description=...)`——description 就是给 LLM 看的 API 文档，我写清了输入格式（如"车次列表 ['Z227']"）来降低传参错误率；② system_prompt 里的工具使用指南，处理模糊和组合场景（如"先查信息再画图"的顺序规则）。

**追问：循环会不会无限跑下去？**
> LangGraph 有 recursion_limit 默认保护（超限抛 GraphRecursionError）。业务上工具都是快查询，正常 1-3 轮就结束；异常场景（RAGFlow 挂了 LLM 反复重试）会被我的 300 秒取块超时先切断。

## Q2.2 四个工具是怎么设计的？（⭐ 高频）

> 设计原则有三条：
> 1. **description 是给 LLM 看的 API 文档**——写清输入格式和示例，能显著降低 LLM 传参错误率；
> 2. **返回格式化文本而非 JSON**——LLM 读文本更稳，且能直接引用进回答；
> 3. **查不到返回提示文本而非抛异常**——让 LLM 能向用户解释"没找到"，而不是整个请求 500。
>
> 四个工具：retriever_tool（RAGFlow 检索，带来源文件名）、query_train_info（按车次号查，支持批量）、query_trains_by_route（按起讫站查，按 G→D→C→Z→T→K 优先级排序）、generate_route_map（Folium 生成自包含 HTML）。
>
> 数据加载做了进程内缓存——9547 车次的 JSON 约 10MB，首次加载 0.4 秒，之后 0.005 秒。

**追问：工具执行失败怎么办？**
> 分两类：可预期的失败（车次不存在）返回提示文本让 LLM 转述；基础设施失败（RAGFlow 连不上）在客户端层捕获返回空结果——但这个设计有已知缺陷：LLM 拿到"未找到"会反复重试检索，每次 4 秒超时，累计拖慢整体。改进方向是加失败计数，连续失败就直接告知用户知识库暂不可用。

**追问：为什么地图用 Folium 生成 HTML 而不是前端画？**
> ① Python 生态没有好的交互地图库，Folium 的定位就是"用 Python 生成 Leaflet HTML"；② 生成的 HTML 自包含（内嵌 Leaflet JS/CSS），前端 iframe 直接加载，前端零地图代码；③ 静态文件由 Nginx 直接服务（Docker 共享卷），不经后端转发。

## Q2.3 System Prompt 里写了什么？为什么重要？

> 两部分：角色设定（铁路专家）+ **工具使用指南**。指南是关键，比如"用户同时要查信息和画地图时，先调 query_train_info 再调 generate_route_map"——没有这条，LLM 可能只调一个工具就回答，或者顺序错乱。实测加了指南后组合意图的工具调用顺序基本正确。
>
> 本质上 system prompt 是在**编译期**给 LLM 注入路由规则，比运行时重试便宜得多。

# 第三部分：并发与流式类提问（职责 2）⭐⭐⭐

## Q3.1 SSE 流式接口的整体架构？（⭐⭐⭐ 必考，简历核心）

> 这是我花精力最多的部分。核心矛盾：**LangGraph 的 agent.stream() 是同步阻塞生成器，而 FastAPI 的 async 端点跑在事件循环上——直接调用会冻结整个服务**。
>
> 解法是四个组件的组合：
> 1. **有界线程池**（8 workers）——所有同步阻塞操作（建流、每次 next()）都 run_in_executor 扔进池子，事件循环只做 await；
> 2. **结束标记对象**——同步生成器的 StopIteration 穿越 asyncio.Future 会被包装成 RuntimeError，破坏迭代语义。用 `_SENTINEL = object()` 在 next() 的包装函数里捕获 StopIteration 返回这个标记，事件循环侧用 `is` 判断标记来退出循环；
> 3. **两层超时**——建流 60 秒（LLM 连接慢）+ 单块 300 秒（工具执行慢），用 asyncio.wait_for 强制限时；
> 4. **错误也走 SSE**——超时/异常时推送 error 事件再发 [DONE] 正常收尾，前端不会无限转圈。

**追问：为什么线程池必须有界？默认的不行吗？**
> 默认 `run_in_executor(None)` 用无界池——并发请求会无限创建线程。而所有请求共享同一个 SQLite 连接，线程爆炸会放大锁竞争。8 是经验值：受 LLM 供应商并发配额限制，再多线程也没用，反而有害。

**追问：为什么用一个标记对象而不是直接捕获 StopIteration？**
> 因为 StopIteration 在 `await` 链路里会被 asyncio 包装成 RuntimeError——这是 Python 的一个经典陷阱：PEP 479 之后生成器里的 StopIteration 会变成 RuntimeError，而通过 Future 传播时语义也被破坏。用一个专门的标记对象表示"流结束了"，用 `is` 判断（不是 ==），从根上规避。

**追问：双层超时的时间怎么定的？**
> 建流 60 秒：覆盖 LLM API 慢连接场景；单块 300 秒：覆盖最慢的工具（地图生成实测 6.5 秒、RAGFlow 异常重试 4 秒×N）。300 秒是"宁可多等也不误杀正常长回答"的取舍——超时后线程里的任务其实还在跑（线程杀不死），只是请求提前返回。

## Q3.2 为什么 /chat 用同步 def、/chat/stream 用 async def？（⭐ 高频）

> **按需选型，不是风格统一**：
>
> `/chat` 是一问一答，用同步 `def`——FastAPI 检测到同步函数会**自动扔进 Starlette 线程池**执行，阻塞发生在工作线程上，事件循环无恙。体验类似 Spring MVC 的每请求一线程，代码最简单。
>
> `/chat/stream` 需要逐块限时、出错时优雅收尾、控制并发数量——这些能力只有 asyncio 的 wait_for 和异常处理能提供，所以必须 async + 自建线程池。
>
> 有人建议统一成 async，我评估后没改：统一会让两个端点争抢同一个 8 线程池，失去故障隔离——现在压测流量打 /chat 占满 Starlette 池（40 线程），流式用户的 8 个槽位毫发无损。

**追问：async 端点里写阻塞代码会怎样？**
> 冻结整个事件循环——所有并发请求无法接收、所有 await 无法恢复。我踩过这个坑：中断修复函数是同步阻塞的（SQLite + 潜在 LLM 调用），最初在 async 端点里直接调用，代码审查时发现后包了一层 run_in_executor。原则是：**async 端点里任何同步阻塞调用都必须走 executor**。

**追问：同步 def 端点为什么就可以随便阻塞？**
> 因为 FastAPI 对同步 def 有自动保护——检测到非协程函数就用 run_in_threadpool 执行，阻塞的是 Starlette 池的工作线程（默认 40 个），事件循环毫发无损。代价是占线程：40 个慢请求占满后第 41 个排队。所以同步端点不是免费的，只是把"冻结整个服务"变成"占用一个线程"。

## Q3.3 前端怎么接收 SSE？（⭐ 高频）

> 用原生 fetch 而不是 axios——因为需要 `response.body.getReader()` 拿 ReadableStream 逐块读，axios 默认攒齐响应才回调，流式就断了。
>
> 读取循环三个关键点：
> 1. **TextDecoder 开 stream 模式**——UTF-8 一个汉字 3 字节，网络分包可能把字切开，`{stream: true}` 让解码器跨包缓冲不完整的字节序列，否则中文随机乱码；
> 2. **跨 read 的事件缓冲区**——TCP 分包不看 SSE 事件边界，一个 `data: {...}\n\n` 可能被切在两个包里。我维护一个 buffer，每次 split 后用 `lines.pop()` 把最后一段（可能是半个事件）留在缓冲区与下次数据拼接。这个 bug 是代码审查发现的，修复后用 7 字节极端分包模拟验证——40 个事件全部完整解析，0 丢失；
> 3. **打字机效果不是定时器**——LLM 每吐一个 token，后端 yield 一个 SSE 事件，前端收到就更新 Vue 响应式数组，重渲染自动发生。打字速度 = LLM 生成速度，前端零额外代码。

**追问：为什么不用 WebSocket？**
> 单向推送场景 SSE 更轻：基于 HTTP、自动重连、代理友好。WebSocket 的双向能力这里用不上，还要处理心跳、协议升级。OpenAI 等主流 LLM API 也都用 SSE。

**追问：Nginx 代理 SSE 要注意什么？**
> `proxy_buffering off`——Nginx 默认攒响应缓冲，会把流式变成"卡半天突然出一大段"；还要 `proxy_read_timeout 300s` 匹配后端超时。这是 SSE 上生产的经典坑。

## Q3.4 [DONE] 结束标记是干嘛的？

> SSE 协议没有"流结束"标志，连接断开可能是正常结束也可能是异常中断。`[DONE]`（借 OpenAI 约定）放在 generate() 的 try/except **之外**，保证后端活着就必发——正常结束是 content 后跟 [DONE]，异常是 error 后跟 [DONE]。所以**它的缺席就意味着进程崩溃或断网这类后端无法控制的中断**——沉默本身就是信号。前端收到后跳过不显示，靠下一次 read 的 done 退出循环。

# 第四部分：多轮记忆与会话修复类提问（职责 3）⭐⭐⭐

## Q4.1 多轮记忆怎么实现的？（⭐⭐⭐ 必考）

> LangGraph 的 SqliteSaver 作为 Checkpointer：ReAct 循环**每走一步**，全量对话状态经 msgpack 序列化写入 SQLite 的 checkpoints 表，按 thread_id 索引。下次同 thread_id 请求，取最新快照反序列化恢复状态——对话无缝继续。
>
> thread_id 设计为 `user_{id}_{session_id}` **双重隔离**：用户维度保证越权访问返回空（安全边界），会话维度支持同一用户开多个独立对话。前端生成 UUID 作 session_id，续聊时从 thread_id 反解回来复用。

**追问：为什么选 msgpack？**
> checkpoint 每步都写、每次请求都读，体积和解析速度直接影响延迟。msgpack 是二进制版 JSON，体积小 20-50%、解析更快。LangGraph 把消息对象序列化成 ExtType(5)，内部结构是 ['模块路径', '类名', {属性}]——我写 checkpoint_parser 反解历史会话时就靠这个格式。

**追问：WAL 是什么？为什么需要？（⭐ 高频）**
> Write-Ahead Logging，SQLite 的读写分离日志模式。默认模式下写库锁全库，读要等写完——8 线程并发会频繁 database is locked。WAL 下写入追加到 -wal 文件、读者读主库+wal 的合并视图，**读写不互斥**。配套还有 busy_timeout=30000（撞锁等待而非报错）和 check_same_thread=False（连接跨线程）。20 线程并发测试验证无锁错误。
>
> 补充一个细节：WAL 里的数据写入即持久化，SQLite 自动 checkpoint（默认累计 4MB）时才搬回主库——搬移是整理动作不是保存动作。

## Q4.2 中断修复机制是怎么设计的？（⭐⭐⭐ 简历亮点，必考）

> **问题**：流式请求 300 秒超时被切断时，Agent 可能正停在"LLM 已输出 tool_calls、工具还没执行"这一步——checkpoint 里留下悬空的 tool_calls。下次同 thread_id 请求时，OpenAI 协议要求 tool_calls 后必须紧跟 tool 消息，LLM API 直接拒绝这种非法序列 → **会话永久损坏**。
>
> **修复**：每个聊天接口入口处调 `_repair_incomplete_tool_calls`——`get_state` 取最新状态，检查最后一条消息是否带未闭合的 tool_calls，是就 `agent.invoke(input=None)` 让 LangGraph 从断点继续、补完工具执行、写回 ToolMessage，状态恢复完整。
>
> **本质**：把"无法恢复的错误"变成"可以自动修复的状态"——一次超时的代价从"会话永久损坏"变成"单次回答失败"。

**追问：invoke(None) 是怎么补完的？**
> input=None 表示不加新消息、从当前状态继续跑图。checkpoint 的最后状态是"LLM 已产出 tool_calls"，图的下一个待执行节点就是工具节点——框架自动把上次没执行完的工具跑掉，ToolMessage 写回，状态闭环。

**追问：补跑工具不会又超时吗？（⭐ 深挖题）**
> 不一定，三个原因：① 原超时往往是**累计**撞上的 300 秒（如 RAGFlow 挂了 LLM 反复重试，每次 4 秒×N 次），而修复补跑的是**一次**工具调用（4 秒）；② 修复路径没有那道 300 秒限时，工具内部有自己的 30 秒超时保护；③ 就算修复再失败，还有后续处理——记日志 → 继续处理 → 前端放弃坏会话换新 session_id，最坏只废一个会话。
>
> 诚实的边界：这是自动修复不是根治——工具慢的根本解决要靠检索失败时快速放弃。另外修复的前提是**工具重复执行没有副作用**：我的四个工具全是只读或覆盖写（地图重新生成覆盖同一文件），重跑无副作用。如果未来加非幂等工具（如订票），修复策略要改成伪造"执行失败"的 ToolMessage。

**追问：为什么只检查最后一条消息？**
> 只有流程被切断才会产生悬空 tool_calls，它必然在序列末尾；中间的都已配对闭合。检查全部是浪费。

**追问：修复函数在 async 端点里怎么调的？**
> 这里我踩过坑：修复是同步阻塞的（get_state 读 SQLite + invoke 可能调 LLM），最初在 async 端点直接调用会冻结事件循环。代码审查发现后包了一层 `_repair_incomplete_tool_calls_async`——run_in_executor 扔进有界线程池。同步端点 /chat 不用包，FastAPI 自动扔线程池。

## Q4.3 checkpoint 二进制反解是怎么回事？（⭐⭐⭐ 简历亮点）

> **背景**：历史会话侧边栏要显示每个会话的预览，但 LangGraph 没有提供读取 checkpoint 的官方 API——状态是 msgpack 序列化的二进制 blob。
>
> **格式**（必须理解才能写解析器）：checkpoint blob 解包后是 {v, ts, channel_values: {messages: [...]}}，每条消息是 ['msgpack', bytes] 的 typed 格式，bytes 再解包是 ExtType(code=5)，data 再解包是 ['模块路径', '类名', {kwargs}]——从类名判断角色（HumanMessage→user，AIMessage→assistant），SystemMessage/ToolMessage 过滤。
>
> **设计思路**：LangGraph 版本升级会改内部格式（dict 包装、__start__ 路径等），所以解析器做了**三种格式的兼容**——消息可能是 ExtType 直接出现、可能是 typed 包装、可能是纯 dict，逐级尝试；channel_values 也兼容 bytes/dict 两种 key；**任何一步失败返回空列表，绝不抛异常**——读历史不能影响主流程。
>
> **测试**：用 LangGraph 官方的 JsonPlusSerializer 构造测试数据，保证与线上格式完全一致——手造 msgpack 容易偏差。

**追问：为什么不用官方 API？**
> LangGraph 2.x 没有暴露"按 thread 读消息列表"的稳定公开接口（有 get_state 但返回的是内部结构，且格式随版本变）。多格式兼容解析 + 全 try/except 保护是务实选择，代价是 LangGraph 大版本升级时可能要适配——解析失败也只是侧边栏预览为空，不影响核心功能。

# 第五部分：安全防线类提问（职责 4）⭐⭐

## Q5.1 三层安全防线分别是什么？（⭐ 高频）

> **第一层：入口校验（源头掐断）**——Pydantic field_validator 在路由函数执行前校验：session_id 白名单正则 `^[A-Za-z0-9_-]{0,64}$`（恶意字符根本进不来）、message 非空且 ≤8000 字符（防空消息和超长文本打爆 token）。校验失败返回 422，不浪费 Agent 资源。
>
> **第二层：参数化查询（核心防线）**——所有含用户输入的 SQL 用 `?` 占位符 + 参数元组，用户输入被转义成数据字面量，不可能逃逸成 SQL 语法。对应 Java 的 PreparedStatement。
>
> **第三层：越权校验（业务隔离）**——所有会话接口检查 `thread_id.startswith(f"user_{current_user.id}")`，不匹配返回空。就算攻击者拿到别人的 thread_id，用自己的 JWT 也读不到。
>
> 三层各自独立：正则拦不住的还有参数化兜着，参数化之外还有前缀校验——一层失效不至于全线失守。

**追问：为什么 session_id 校验这么严？**
> 它会被拼进 thread_id 并作为 SQLite 查询条件——不限制字符就是注入入口。虽然第二层参数化能拦住，但多层防御要求在源头也掐断。

**追问：表名列名能参数化吗？**
> 不能，SQLite 的参数化只支持值。如果未来要支持动态列名，必须用白名单校验（`if col not in ALLOWED_COLUMNS: raise`）而不是拼接。我项目里列名都是写死的，没这个需求。

## Q5.2 JWT 认证怎么做的？密码怎么存的？

> **密码**：argon2 哈希（内存困难型，抗 GPU 爆破，比 bcrypt 强）。注册时 `ph.hash()`，登录时 `ph.verify()`，只捕获 VerifyMismatchError。有个测试坑：库里存明文时 argon2 抛 InvalidHashError（不是 VerifyMismatchError），不会被捕获导致 500——所以测试夹具必须用 ph.hash() 造数据。
>
> **JWT**：HS256 签名，5 小时过期，payload 的 sub 存用户名。安全底线：JWT_SECRET_KEY 未配置时直接抛错——宁可启动失败，也不用默认的弱密钥蒙混过关。decode 时显式指定 algorithms=["HS256"] 防算法混淆攻击。
>
> **前端配合**：手写 JWT payload 解析（base64url 转换 + UTF-8 处理），isTokenExpired 提前 10 秒判定过期，App.vue 每 30 秒检查一次，覆盖用户长时间停留在页面上、路由守卫不会触发的场景。

**追问：为什么 token 放 localStorage 而不是 cookie？**
> localStorage 实现简单、跨域友好（配合 CORS）；XSS 风险靠 Vue 的模板转义（v-html 只用于受控的 markdown 渲染）缓解。HttpOnly cookie 更防 XSS 但需要 CSRF 防护和同站配置，个人项目权衡后选了 localStorage。这是有争议的取舍，生产环境我会重新评估。

# 第六部分：数据同步与许可类提问（职责 5）⭐⭐

## Q6.1 数据同步子项目是怎么设计的？（⭐ 高频）

> 背景：车次时刻数据每天变，静态 JSON 会过期。我参考了一个 GPL-3.0 的开源爬虫项目（RailRhythm），但**没有复制它的代码**——GPL 有传染性，直接集成会迫使整个项目转 GPL。
>
> 最终方案是 **B+C 组合**：
> - **B（隔离）**：独立子项目 `train_sync/`，与主项目只通过数据文件交互（JSON），运行时无代码链接；
> - **C（原创）**：爬虫从零实现——只用 12306 的两个公开 HTTP 接口（train_no 搜索 + 时刻表详情），多线程 8 并发、5 次重试、被反爬时自动放弃本次更新。
>
> 数据流：爬取 → 原始格式存 raw/ → transform.py 转换为主项目格式（原子写入，防写一半崩溃）→ 质量检查（<1000 车次视为被反爬，放弃更新）→ 替换主项目 data/。**失败保护**：任何环节失败都保留旧数据，主项目永远有可用数据。

**追问：为什么确信这样不违反 GPL？**
> GPL 的传染边界在"衍生作品"——代码级链接、库依赖会构成衍生。独立进程 + 数据文件交互是业界常用的隔离方式（类似用 GCC 编译出二进制再用）。严格说数据文件的边界有法律灰色地带，最稳妥是咨询原作者——但我的实现连代码都没复制，只参考了公开接口的行为，风险极低。主项目保持 CC BY-NC 不受影响。

**追问：爬虫怎么应对反爬？**
> 四招：① 控制并发（8 线程，不贪快）；② 失败重试（5 次，间隔递增）；③ 质量检查（车次数低于阈值判定被反爬，放弃本次更新而不是写入残缺数据）；④ User-Agent 可配置。实测用 RailRhythm 作者提供的真实数据验证转换链路：9628 个车次转换成功，主项目工具正常读取。

**追问：为什么全量重爬而不是增量？**
> 全量简单可靠：每天一次全量（约 1 万车次），数据自洽无合并冲突。增量要处理"车次停开、时刻变更、新增"三种 diff，复杂度高且容易出脏数据。数据量级（万级）下全量的成本可接受——**简单性优先，规模到了再优化**。

# 第七部分：测试体系类提问（成果 1）⭐⭐⭐

## Q7.1 测试体系是怎么分层的？（⭐⭐⭐ 必考）

> 四层，每层测不同的东西：
>
> | 层 | 内容 | 例子 |
> |---|---|---|
> | 单元 | 纯函数逻辑 | schemas 校验、settings 解析、llm 工厂 |
> | 集成 | API 端到端（Mock 外部依赖） | 注册→登录→聊天全链路，Mock 数据库链和 Agent |
> | 并发 | 真实组件多线程 | 20 线程 + 真实 SqliteSaver，验证无锁错误和 thread_id 隔离 |
> | 格式兼容 | 真实序列化器 | 用官方 JsonPlusSerializer 构造 checkpoint blob 测反解 |
>
> 总计 90 个用例全通过。覆盖率总 39%——核心模块高（agent 61%、tools 81%、auth 82%、database 100%），ragflow 相关 0% 是预期（需要真实服务）。

**追问：Mock 策略是怎么做的？（⭐ 深挖）**
> 五个关键手法：
> 1. **伪造用户**：MagicMock 但 id/username 必须是真实类型（thread_id 拼接用 int）；
> 2. **绕过认证**：`app.dependency_overrides[get_current_user] = lambda: user`，用完必删防污染；
> 3. **替换 Agent**：直接 patch 模块级变量 `backend.api._agent`；
> 4. **数据库链**：`mock_db.query.return_value.filter.return_value.first.return_value = None` 链式 mock；
> 5. **流式测试必须用真 AIMessage**——后端有 isinstance 检查，MagicMock 过不了。
>
> 还有 conftest 的 autouse fixture 在每个测试前后重置单例，防 mock 残留污染。

**追问：并发测试怎么写的？**
> 真实 SqliteSaver + 假 LLM（FakeMessagesListChatModel，不联网）+ 20 线程。三个断言：并发 invoke 无 database is locked、不同 thread_id 状态互不串话、AgentService 的连接确实开了 WAL。假 LLM 是关键——测并发不依赖真实 API key，CI 上也能跑。

**追问：覆盖率 39% 是不是太低了？**
> 分开看：核心业务逻辑（Agent/API/工具/认证）覆盖 60-100%，低的是 ragflow_init/migrate（0%）——它们需要真实 RAGFlow 服务和 Docker 环境，mock 的价值有限（测的是"mock 对 mock"）。我的判断是：**为外部依赖的胶水代码硬凑覆盖率是虚假指标**，核心逻辑的测试密度才是真的。如果要提，方向是给 ragflow_client 加 respx 之类的 HTTP mock 测试。

## Q7.2 有没有测试发现过真实 bug？（⭐ 体现测试价值）

> 有，最典型的是 session_id 校验那个全接口 500。压测脚本一跑，所有 /chat 请求 500——排查发现 `_SESSION_ID_RE` 定义为不加注解的类属性，Pydantic v2 把 `_` 前缀属性判定为私有属性，包装成 ModelPrivateAttr 且从 __dict__ 移走。关键是对称性破坏：**类级访问（cls.xxx）返回包装对象不解包，实例级访问才返回真值**——而 field_validator 必然是 classmethod（校验在实例创建前），只能用 cls，就踩中了。
>
> 这个 bug 还有个隐蔽点：`_` 前缀让 Pydantic 走"私有属性"分支**悄悄包装而不报错**，类定义毫无异常——如果常量名不带下划线，Pydantic 会在类定义时立刻报 PydanticUserError，当场就能发现。所以最终修复是 ClassVar 注解 + 去掉下划线，让同类错误将来在类定义时就暴露。

# 第八部分：压测与性能类提问（成果 2）⭐⭐⭐

## Q8.1 压测是怎么做的？结果如何？（⭐⭐⭐ 必考）

> 自研压测脚本（纯 Python，httpx + 线程池，零额外依赖）：自动注册测试用户拿 JWT → 并发打 /chat 非流式接口 → 统计 QPS、P50/P95/P99、成功率 → JSON 导出结果。
>
> 实测（并发 5 / 10 请求）：**成功率 100%**，QPS 0.4，平均延迟 12.5 秒，P95 27.2 秒。
>
> **关键在解读**：延迟的构成是 LLM 推理（10-15 秒）+ RAGFlow 未启动时 Agent 反复重试检索（每次 4 秒超时 × N 次）。系统本身（认证、路由、checkpoint 持久化）开销毫秒级。**结论：瓶颈在外部依赖，不在应用层**——这个结论比数字本身有价值，它指明了优化方向是减少无效重试和换更快的模型，而不是加机器。

**追问：QPS 0.4 是不是太低了？**
> 单看数字确实低，但要拆开看：这是 LLM 问答接口，单请求本来就要 10 秒+（LLM 生成时间），QPS = 并发数 / 单请求耗时，5 并发 / 12.5 秒 ≈ 0.4 是必然结果。**对比对象应该是"应用层自身开销"**——把 LLM 时间去掉，认证+路由+持久化只占几十毫秒，这部分开销才是我的代码贡献的。要提 QPS，方向是加并发线程数（受 LLM 配额限制）、流式接口降低感知延迟、检索失败时快速放弃减少无效等待。

**追问：压测发现了什么 bug？**
> 就是 session_id 那个全接口 500——压测一跑成功率 0%，日志里全是 AttributeError。这验证了压测的双重价值：既量化性能，又当集成测试暴露运行时 bug。

**追问：怎么保证压测数据可复现？**
> 记录环境信息（本地 uvicorn 单进程、LLM 模型、线程池大小）、固定消息内容、多次运行取稳定值。脚本支持 --output 导出 JSON 结果。诚实说：LLM 响应时间有波动，绝对值会漂，但"瓶颈在外部依赖"这个结论是稳定的。

## Q8.2 如果要优化性能，你会从哪入手？（⭐ 高频开放题）

> 按投入产出排序：
> 1. **检索失败快速放弃**（最高优先）：RAGFlow 失败时直接返回"知识库不可用"，消除 4 秒×N 的重试放大——这是压测实测的最大延迟源；
> 2. **流式降低感知延迟**：/chat/stream 已经做了，首 token 时间远小于总时长，用户感知好很多；
> 3. **换更快模型或加缓存**：高频问题（如热门车次）缓存回答；
> 4. **调线程池**：AGENT_THREAD_POOL_SIZE 可配，但受 LLM 并发配额限制，盲目加大无效；
> 5. **不做的**：数据库优化——毫秒级开销，优化它是过早优化。

# 第九部分：隐患修复类提问（成果 3）⭐⭐⭐

## Q9.1 你说"主动发现并修复 3 个隐患"，具体讲讲？（⭐⭐⭐ 必考）

> **隐患 1：async 端点同步阻塞调用冻结事件循环**
> 中断修复函数是同步阻塞的（SQLite 读取 + 潜在 LLM 调用），最初在 /chat/stream（async）里直接调用——修复期间（最坏 30 秒）整个事件循环冻结，所有并发请求卡死。代码审查时发现，修复方式是包一层 run_in_executor 扔进有界线程池；同步端点 /chat 不用包（FastAPI 自动扔线程池）。
>
> **隐患 2：SSE 事件被网络分包切断丢 token**
> 前端每次 read 单独 split('\n\n')，但 TCP 分包不看事件边界——一个事件被切在两个包里时，两半都 JSON.parse 失败，丢 token（不崩）。修复是加跨 read 的缓冲区，split 后用 pop 把最后一段（可能是半个事件）留缓冲拼接。验证方式：故意用 7 字节小块读取（比真实网络恶劣一个数量级），40 个事件全部完整解析 0 失败。
>
> **隐患 3：静态目录与生成路径不一致**
> 地图生成端写 data/maps，后端静态挂载的却是 frontend/public/maps——Docker 里地图 404。修复是两端统一读 maps_output_dir 环境变量（Docker 注入共享卷路径，本地默认 data/maps）。
>
> **共同点**：三个都是"功能在理想路径下正常、异常/边界场景才坏"的问题——靠代码审查的系统性排查（阻塞点、分包边界、路径一致性）发现，不是等用户报障。

**追问：怎么系统性排查这类隐患的？**
> 三个检查清单：① **async 端点里逐行找同步阻塞调用**（SQLite/requests/文件 IO）；② **流式解析对齐协议边界**（事件完整性、字节序列完整性）；③ **同一资源的所有引用点对齐**（生成端/服务端/部署配置的路径）。这套清单后来成了我 review 自己代码的习惯。

## Q9.2 修复时怎么验证的？（⭐ 追问）

> 每个修复都有对应的验证手段：
> - 事件循环冻结：修复前后对比并发请求的响应情况（修复前其他请求卡 30 秒，修复后不受影响）；
> - SSE 分包：写验证脚本故意用 7 字节小块读流（模拟最恶劣分包），断言 0 解析失败；
> - 路径不一致：本地复现 404 → 修复后 200，Docker 环境用环境变量注入验证。
> 另外每次修复都跑全量 90 个测试防回归，修复本身也补了回归测试（如 session_id 校验的正反用例）。

# 第十部分：工程化类提问（成果 4）

## Q10.1 CI 流水线是怎么设计的？

> GitHub Actions 四个并行 job：① Ruff lint（只查致命错误，快速失败）；② Python 3.10/3.11 矩阵测试 + pytest-cov 覆盖率 + pip 缓存；③ 前端 type-check + build（Node 22 + npm 缓存）；④ Docker 双镜像构建验证（push: false 只验证可构建）。顶层配 concurrency 组——同分支新 push 自动取消旧跑，省额度。

## Q10.2 Docker 部署有什么设计点？

> 四个：① **层缓存优化**——requirements.txt 先 COPY 单独装依赖，代码改动不触发重装；② **共享卷地图链路**——后端生成地图写 maps_data 卷，Nginx 只读挂载直接静态服务，不经后端转发；③ **SSE 反代配置**——proxy_buffering off（否则流式被缓冲破坏）+ read_timeout 匹配后端；④ **前端多阶段构建**——Node 构建 → Nginx 托管，镜像小。

## Q10.3 为什么写 34 章构建手册？

> 两个动机：① 这个项目踩了 20+ 个坑，不记下来下次还踩；② 复习面试时需要"每一行代码为什么存在"的依据。手册按施工顺序组织（配置→认证→Agent→API→RAG→前端→测试→部署），每章带设计决策、踩坑记录、面试考点——它本身就是我面试准备的载体。

# 第十一部分：压力测试题（面试官故意刁难）

## Q11.1 这就是个个人项目吧？能和企业级比吗？

> 承认差距，但强调方法论等价："是的，它是个人项目，用户量级和生产环境没法比。但我认为**工程方法的密度**是可以迁移的：三层安全防线、四层测试体系、压测定位瓶颈、许可合规隔离、代码审查清单——这些在企业项目里同样是正确做法，只是企业级还要加多实例部署、分布式锁、监控告警、灰度发布。我缺的是大规模场景的经验，不是工程意识。"

## Q11.2 你的 QPS 才 0.4，生产环境怎么办？

> 见 Q8.2 的回答，核心：拆解延迟构成证明瓶颈在外部依赖；给出优化路线（减少无效重试→流式→缓存→并发）；说明 0.4 是 LLM 问答接口的必然结果（5 并发/12.5 秒），不是应用层能力上限。

## Q11.3 如果用户量涨 100 倍，哪里先崩？

> 按顺序推演：
> 1. **LLM 供应商配额**——最先到顶（外部依赖，加机器没用）；
> 2. **SQLite 写并发**——WAL 支撑的写并发有限，checkpoint 写入会排队 → 换 PostgreSQL（SQLAlchemy 已解耦，checkpointer 换 PostgresSaver）；
> 3. **单进程 uvicorn**——事件循环单点 → 多 worker / 多实例 + Nginx 负载均衡（但注意 SqliteSaver 的连接是进程级的，多实例要共享存储）；
> 4. **RAGFlow 单实例**——它自己也要扩容。
> 这个推演展示的是"知道系统的极限在哪、崩的顺序是什么"——比"我能扛十万并发"的空话有价值。

## Q11.4 你的测试都是 Mock 的，能证明什么？

> 分层回答："Mock 测的是**我的代码逻辑**（路由、校验、状态转换、错误处理），不是外部服务的正确性——后者本来就不该是我的测试范围。而且不是所有测试都 Mock：并发测试用真实 SqliteSaver、格式测试用官方序列化器、压测打真实后端。Mock 的边界我划得很清楚：**外部依赖 Mock，内部逻辑真实**。"

## Q11.5 为什么不用向量数据库自己搞 RAG，要依赖 RAGFlow？

> 权衡：RAGFlow 提供文档解析、分块、向量化、检索的完整流水线，237 篇文档的管理拿来就能用；自建 Chroma 要自己处理解析、分块策略、更新流程。代价是引入一个重依赖（五个容器）和它的上游 bug（我打了两个运行时补丁）。如果重来，小规模场景我会考虑轻量方案（Chroma + 简单分块），但这个项目的文档量和"少自己造轮子"的需求下 RAGFlow 合理。**关键是检索层是 REST 解耦的，换实现只动 ragflow_client.py 一个文件。**

## Q11.6 你说修了 Pydantic 的 bug，那是 Pydantic 的锅还是你的锅？

> 都不是，是**框架规则与命名约定的交互**："Pydantic 的规则是模型类属性必须有明确角色（字段/ClassVar/私有），`_` 前缀 + 无注解会被判定为私有属性——这个判定本身是合理的。我的错误在于不了解这个规则，用了会触发它的命名。但这个坑的隐蔽性值得说：`_` 前缀让 Pydantic 悄悄包装而不报错，如果常量名不带下划线，类定义时就会报 PydanticUserError 当场发现。所以修复后我不仅加了 ClassVar，还去掉了下划线——让同类错误将来在类定义时就暴露，而不是推迟到线上。"

## Q11.7 前端也是你写的？后端为主的人写前端有什么体会？

> 是，全栈独立完成。体会最深的一点：**前后端对"流式"的理解必须对齐**——后端 SSE 的事件边界、前端的分包缓冲、TextDecoder 的字节流处理，任何一端理解错都会出隐蔽 bug（比如中文跨包乱码、事件跨包丢失）。这段经历让我 review 接口时会同时看两端的边界假设。
