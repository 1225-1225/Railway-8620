# OSM 数据层

从 OSM 原始数据构建**铁路参考数据**的离线脚本。运行时（`agent/`）只消费 `out/` 下的产物，
不直接读 OSM 文件。

## 数据来源

- Geofabrik 中国快照：<https://download.geofabrik.de/asia/china-latest.osm.pbf>
- 许可：ODbL（需保留 attribution）
- 放置路径：`data/pbf/*.osm.pbf`（已在 `.gitignore` 中排除）

## 依赖

```bash
pip install osmium        # 预编译轮子约 1.9 MB，无 GDAL 依赖
```

## 为什么用 .osm.pbf 而不是 GPKG

| | `.osm.pbf` | `.gpkg`（GDAL 导出） |
|---|---|---|
| 体积 | 1.5 GB | 9.7 GB |
| 标签 | 原生 dict | `other_tags` 字符串，需正则反解 |
| 关系成员顺序 | 保留 `role` 与排列 | 合成为整体几何后**丢失** |
| 几何 | 库直接给坐标 | 需自写 WKB 解析（约 150 行）|

GPKG 仅在需要 QGIS 肉眼核查时临时导出。

## 数据源：为什么用 way 的 name 标签，不用 route 关系

**这是本项目最重要的一条经验。**

`route=railway` 关系收录极不完整。实测同一批线路：

| 线路 | 关系成员 way | `name` 标签 way | 关系漏掉 |
|---|---|---|---|
| 沪昆线 | 10 | 5360 | **99.8%** |
| 京沪线 | 2764 | 2762 | 0.4% |
| 京哈线 | 2078 | 2080 | 0.1% |

若只读关系，沪昆线几乎"凭空消失"（只剩 12 km）。

改用 `railway=rail` 且带 `name` 的 way 作数据源：

- 覆盖线路名 **3244 条**（关系法仅 1932 条，+68%）
- 覆盖 way **24 万个**
- 站点有线路归属比例 **92.6%**（关系法仅 52.8%）

## 里程为什么不能直接求和

OSM 把**每一股道**都画成独立 way，全部带同一个 `name`：

```python
{'railway':'rail','name':'京沪线','oneway':'yes'}              # 上行
{'railway':'rail','name':'京沪线','railway:track_ref':'II-II'}  # 下行
{'railway':'rail','name':'京沪线','passenger_lines':'3'}        # 第三股道
```

因此"所有 way 长度求和"得到约 2 倍里程（实测京沪 3093 vs 实际 1463，2.11×）。

**解法**：把该线路所有 way 建成图，取**地理上最远的一对端点**，在图上求**最短路** ——
最短路天然只走其中一条轨道。

再对多连通分量做「几何覆盖率去重」（平行轨道被覆盖 ≥50% 则丢弃），
最后在 >50 km 的跳变处切开，各段独立保留。

## 两站之间有多条线路时怎么选

这是运行时消歧的核心。**判据按优先级**：

1. **车次类型先验**（最强）：`G/D/C` → 高速线；`K/T/Z` → 普速线
2. **线路长度**：更长者更可能是主干线
3. **线路名特征**：含"联络线/走行/绕行/专用线"的降权
4. **绕行比质量门**：路径/直线比值须在 0.5~3.0，否则换下一条

线路等级判定规则（`RouteGeometry.line_grade`）：

| 判定 | 命中词 |
|---|---|
| `high_speed` | 高速、客专、高铁、城际 |
| `conventional` | 联络线、绕行、走行、疏解、专用线、货线、环线、支线 |
| `other` | 其余（含纯股道名如 `1道`）|

实测效果（京沪走廊）：

```
G1  (高速): 北京南->天津南  共同线路 1 ['京沪高铁']
T35 (特快): 北京->沧州      共同线路 1 ['京沪线']
G1  -> 3/3 段真实轨道，里程 1313 km（实际约 1318）
T35 -> 5/5 段真实轨道，里程 1077 km
```

## pyosmium 4.x API 备忘

实测踩过的坑：

```python
# 标签迭代产出 Tag 对象，不是字符串
for t in tags:                 # t.k / t.v
    if t.k.startswith("name:zh"): ...

# Header 没有 has_option()；多版本判断是属性不是方法
h = osmium.io.Reader(p).header()
h.has_multiple_object_versions    # bool

# 关系成员是位置参数 (ref, mtype, role)，且不在 mutable 命名空间下
M = osmium.osm.RelationMember
M(100, "w", "forward")

# 【性能关键】必须用 FileProcessor + Filter，不能用 SimpleHandler 全量回调
fp = osmium.FileProcessor(path, osmium.osm.NODE, thread_pool=osmium.io.ThreadPool(8))
fp.with_filter(osmium.filter.IdFilter(needed_ids))       # C++ 层过滤
fp.with_filter(osmium.filter.KeyFilter("railway"))       # 按标签键过滤
```

**性能实测**（扫描 1.5 亿节点找 5 万个）：

| 方案 | 耗时 |
|---|---|
| `SimpleHandler` 全量回调 | 698.6 s |
| `FileProcessor` + `IdFilter` + 8 线程 | **11.1 s** |

**63 倍差距**。`locations=True` 建全国节点索引更慢（实测 36 分钟），应避免。

### `check_geometry.py` —— 几何异常检测（只读）

替代「肉眼判断有没有穿山体」这类不可自动化的检查。

```bash
python data/osm/check_geometry.py                 # 全量，长度 ≥50km 的线路
python data/osm/check_geometry.py --top 20        # 每类列出 20 条
python data/osm/check_geometry.py --line 湘桂线    # 只看一条
```

三类检测：

| 类型 | 判据 | 含义 |
|---|---|---|
| 真实折返 | 夹角 >150° **且凸起 >0.3km** | 拼接错误（凸起小的是共线抖动，不算）|
| 异常长跨 | 单跨 >25km（超长跨度）或 >15km 且转角 >45° | OSM 缺节点 / 可能缺拐点 |
| 绕行比 | 里程 / 端点直线 >2.5 | 绕远，通常是环形线或错配 |

**当前状态**（合计 35 处 / 530 条线路）：

```
真实折返  23 处   凸起 0.37~1.93km，均为真实小半径弯道
异常长跨  12 处   OSM 数据缺口（西部、山区）
绕行比>2.5 2 条   广深环线 3.77 / 함북선边境段 3.53
```

结论：**没有一处是拼接 bug**，详见下节核查记录。

### 几何异常核查记录（2026-11-11）

用户肉眼核查时提出「看不出有没有穿越山体」，于是把这一判断转成可量化的检测，
并对全部异常逐条溯源。结论：**24 处异常没有一处是 bug**。

#### 证据 1：原始链上折返数为 0

对 5 条代表性线路重建**未降采样**的原始链（`assemble_line` 的直接输出）：

| 线路 | 原始点数 | 原始折返数 |
|---|---|---|
| 兰新线 | 8896 | **0** |
| 成昆线 | 7662 | **0** |
| 杭温高速线 | 601 | **0** |
| 水红线 | 1408 | **0** |
| 内六线 | 4403 | **0** |

说明拼接过程本身没有制造折返。降采样后出现的"折返"是采样点稀疏造成的视觉现象。

#### 证据 2：长跨在原始链上就存在

铜蒲线 26.3 km、石太线 24.1 km 的单跨，在**未降采样**的原始链上就已经是单跨。
这是 OSM 在该处没有采集中间节点（西部戈壁、山区），不是算法丢弃。

以青藏线柴达木盆地为例，那一带铁路本身笔直，33 km 无弯曲是真实情况。

#### 证据 3：凸起高度量化真假弯道

关键判据 —— 折返点相对前后点连线的垂直距离（`triangle_height_km`）：

| 线路 | 凸起 | 判定 |
|---|---|---|
| 宝成线 @10 | 1.93 km | 真实弯道 |
| 成昆线 @121 | 1.47 km | 真实弯道 |
| 内六线 @100 | 1.39 km | 真实弯道 |
| 包西线 @18 | 1.21 km | 真实弯道 |
| 大准铁路 @79 | 0.86 km | 真实弯道 |
| 杭温高速线 @1 | 0.37 km | 真实弯道（临界）|
| 兰新线 @423 | 0.29 km | 共线抖动 |
| 广惠城际线 @40 | 0.21 km | 共线抖动 |
| 成昆线 @130 | 0.18 km | 共线抖动 |

采样密度是 **3.3 km/点**（30 点/100km），凸起 0.3–1.9 km 对应图上 5–30 度的转角，
就是正常的小半径弯道。凸起 <0.3 km 的三点几乎共线，只是方位角算法算出了接近 180°。

因此 `check_geometry.py` 把 **0.3 km 作为凸起阈值**，低于此值不报。

### 一次失败尝试：Douglas-Peucker 替代等距降采样

为解决"降采样后出现折返"，曾尝试用 DP 折线简化替代等距抽样。结果：

| 指标 | 等距降采样 | DP 简化 |
|---|---|---|
| km/点 | **3.35** | 9.57 |
| >100km 且点数 <20 的线路 | 0 条 | **120 条** |
| 异常长跨（>25km） | 12 处 | 1061 处 |

DP 在长直线上只保留首尾两点，导致线路形状严重失真。已完全回滚。

**教训**：去抖动与降采样是两件事，必须分层：

- 去抖动作用于原始链（`despike`，5 点中位数）
- 降采样只负责降低点数，不做形状处理

### 分段拼接为什么必须按主轴排序

线路被切成多段时，各段方向可能相反。用「端点最近」贪心拼接会把
方向相反的段硬接在一起，产生 30km 尺度的折返（实测湘桂线 34.7km/160°、
京哈线 33.5km/155°、中老昆万线 29.8km/155°）。

正确做法（`stitch_pieces_along_axis`）：

1. 用所有分段端点拟合线路主轴方向
2. 每段投影到主轴，得到区间 `[t_min, t_max]`
3. 按 `t_min` 排序
4. 拼接时方向取「使 t 递增」的那一端

### 里程基准的坑

`verify.py` 的 `BASELINE` 已人工核对，但要注意**同名不同线**：

| 名称 | 里程 | 说明 |
|---|---|---|
| 沪昆高速线 | 2264 km | 客运专线 |
| 沪昆线 | 2690 km | **普速**，上海-昆明 |
| 兰新线 | 2360 km | 兰州西-阿拉山口**全线** |
| （兰新兰州-乌鲁木齐段）| 1892 km | 常被误当作全线 |

把 2264 套到 `沪昆线`（普速）上会得出错误的 +12.6% 偏差；
把 1892 套到 `兰新线` 上会得出错误的 +25% 偏差。两者都已修正。

## 为什么不实现 build_station_alias

曾计划做一个「12306 站名 → OSM 要素 ID」的人工映射表。实测证明**没有必要**。

抽样 200 车次，非真实段 162 段，归因如下：

| 原因 | 数量 | 占比 | 映射表能否解决 |
|---|---|---|---|
| 两站之间无共同线路 | 141 | **87%** | ❌ |
| 有共同线路但被质量门拒 | 19 | 12% | ❌ |
| 站名找不到 | 2 | **1.2%** | ✅ |

映射表只能解决 1.2% 的问题。而 87% 的主因是：

```
福田(1线)     -> 香港西九龙(3线)   交集为空
深圳坪山(1线) -> 深圳北(4线)       坪山只连 1 条支线
赣州西(0线)   -> 南昌东(4线)       赣州西 0 条线路归属
```

这是线路数据覆盖问题，不是站名问题。放宽吸附半径的收益也很低：

| 吸附半径 | 站归属率 | 车次真实轨道提升 |
|---|---|---|
| 3 km（当前） | 92.6% | — |
| 5 km | 94.3% | — |
| 8 km | 95.9% | **仅 +2.5%** |

代价是把隔壁线路的站误吸进来。**不值得做**。
